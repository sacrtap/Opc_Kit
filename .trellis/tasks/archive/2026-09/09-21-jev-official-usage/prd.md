# browser-with-typesafe: adopt Jev's official 3-layer usage

## Goal

The current skill fails the A/B because it uses Jev the wrong way. Research across
`madewithjev.com/categories/agents-and-browsers` (60 builds) and the official
`browser-use/jev-ultrafast` implementation converges on one fact: Jev is a **selector**, not a
generator. Every successful build (WebMCP 49/49, Flights 7s/$0.004, Stagehand $0.001) splits one
browser step into three layers:

| Layer | Job | Model |
| --- | --- | --- |
| select | choose the next operation + target from a discrete action space | **Jev** |
| generate | produce the field value / search text Jev cannot | **small fast LLM** |
| execute | a11y/DOM snapshot → indexed action space → perform the chosen action | harness |

Two of those facts defeat the current skill directly:

1. **Jev cannot generate arbitrary text.** The official WebMCP build states it outright ("Jev
   can't generate arbitrary text, which you need for tool arguments"). A text-entry helper is not
   an optimization, it is the missing half of the design. This skill currently forbids text entry
   (`TEXT_ROLES` are "never auto-discovered; the host enters text").
2. **Jev is strong at explicit action selection, weak at multi-step DOM navigation.** The official
   docs acknowledge weaker accuracy on questions requiring several reasoning steps. The current
   wizard fixture tests exactly the weak case (10-step click navigation), so it measures the
   skill at its worst.

This task adopts the official 3-layer design and re-measures on a flow that exercises it: search +
filter + form.

## Context — decisions already confirmed with the user

- Fill helper model: `bifrost/sensenova/deepseek-v4-flash` (free, cost 0).
- Measurement fixture: search + filter + form (state-dependent: results render only after the
  query; the form appears after a result is selected).
- Success criterion: **unchanged** — arm B ≤ 0.8 × arm A on BOTH tokens (uncached+output) and time
  per mechanical action, reproduced across two consecutive rounds.
- Host model stays free (both arms), per the standing "free models only" constraint.
- omp tab confirmed to expose `type`/`fill` on both the tab and `ref()` element handles.

## Requirements

### R1 — Fill operation + text helper

- Add a `fill` action that targets a `TEXT_ROLES` node. Jev only selects the operation and the
  target; the value is generated by the configured fill model, never by Jev, never hardcoded.
- The fill helper is an OpenAI-compatible chat/completions call to `bifrost/sensenova/deepseek-v4-flash`,
  instructed to return exactly one JSON object `{"text": "<value>"}` derived from the goal and the
  field's role/name/label. A missing, non-string, empty, or over-long value fails the action (the
  run hands back), never guesses.
- Extend the adapter contract with `type(ref, text)`:
  - omp: `tab.ref(ref).fill(text)`
  - playwright: `page` element `fill(text)`
  - codex: `tab` type/insert via the Computer Use contract (contract-tested only, as today)
- Safety: `fill` is offered only for `TEXT_ROLES` nodes, and `denyNames`/`requireHostNames` continue
  to apply. Submission is never auto-triggered: a fill action never presses Enter/Submits; the host
  remains responsible for any consequential submit/send/publish step.

### R2 — Multi-question decision

- Refactor `decide()` so ONE request asks `operation` (choice over the available operation kinds:
  click / fill / scroll / press / reload / DONE / BLOCKED / WAIT) plus one target question per
  available operation (`click_target`, `fill_target`, …), evaluated in parallel against the same
  state.
- The executor consumes only the target head that matches the selected operation; the other heads
  are ignored. This mirrors the official "two decisions, one network round trip".
- Validate every head's response defensively (a head whose answer is absent/invalid degrades rather
  than failing the whole request, except the selected operation's own head, which must be valid).

### R3 — State-dependent fixture (search + filter + form)

- New fixture flow, correctness reported by the page itself (reuse the existing report hook):
  1. type a query into the search box (value checked by the page against the query in the prompt)
  2. results render only after a correct query
  3. pick the result matching the prompt (target selection among similar rows)
  4. a form renders; fill one or more fields with values from the goal
  5. the page reports `ok` only when the query, selection, and field values all match
- The flow is genuinely state-dependent: later controls do not exist until earlier steps complete.

### R4 — Measure under the unchanged criterion

- Both arms, 3 samples each, free host model, correctness from the fixture's own report.
- Record per arm: wall time, time per mechanical action, host turns, uncached input / output tokens,
  and (arm B only) Jev decision latency + fill-helper usage.
- Criterion: B ≤ 0.8 × A on tokens AND per-action time, reproduced across two consecutive rounds.

### R5 — Report honestly and update docs

- Docs (SKILL.md, skill README, both guides, root READMEs, CHANGELOG) must describe the fill helper,
  its safety boundary, and the measured result. If the criterion is not met, that is the published
  result; never re-scope the metric until it is.

## Constraints

- **Safety bounds are not negotiable**: origin allowlist re-check, stale-decision discard,
  policy-bounded controls, host-side verification of DONE. A `fill` never auto-submits.
- **Free models only** for testing/configuration (host and fill helper).
- **Do not re-publish** the existing 3-action / 15-action numbers.
- **Comparable arms**: any flag applies to both arms.
- Host is omp; codex/playwright adapters are contract-tested only unless a runtime appears.
